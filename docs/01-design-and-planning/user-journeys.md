# User Journeys

## 1. Overview

The website should support several distinct types of visitor while maintaining a consistent and straightforward experience.

The primary journey is for software engineering recruiters and hiring managers. The secondary journey is for technically experienced engineers and university admissions staff.

A separate administrative journey exists for managing website content through the CMS.

The journeys should demonstrate how the website moves visitors from an initial impression towards deeper engagement or contact.

---

## 2. Recruiter Journey

The recruiter is likely to have limited time and may initially be evaluating Joe alongside many other candidates.

The website should therefore communicate the most important information immediately.

### Journey

```text
Homepage
    ↓
Name + Introduction
    ↓
Featured Project
    ↓
Quick Project Summary
    ↓
Visual Evidence
    ↓
Contact / LinkedIn / GitHub
```

The recruiter should immediately be able to identify:

- Joe Waldron's name.

- His interest in software engineering.

- His connection to the automotive industry.

- His strongest current project.

- A clear route to contact him.

The featured project should provide enough curiosity to encourage the recruiter to investigate further.

The recruiter should then be able to quickly:

- Read a project summary.

- See evidence that the project is real.

- Visit the GitHub repository.

- View LinkedIn.

- Contact Joe.

- Download the CV.

The journey should not require the recruiter to understand the entire website before being able to make contact.

---

## 3. Technical Engineer Journey

A technically experienced visitor should be encouraged to investigate the engineering behind the projects.

### Journey

```text
Homepage
    ↓
Featured Project
    ↓
Project Gallery
    ↓
Project Overview
    ↓
Technical Documentation
    ↓
Testing / Results
    ↓
GitHub / External Resources
    ↓
Other Projects
```

The featured project should initially create curiosity rather than immediately presenting every technical detail.

Once the visitor opens the project, visual evidence should provide an immediate indication that the work is genuine.

The visitor should then be able to progressively explore:

- What problem was being solved.

- How the project was researched.

- How it was designed.

- How it was implemented.

- How it was tested.

- What results were achieved.

- What challenges were encountered.

- What could be improved.

The visitor should be able to move from one project to another without returning to the homepage.

---

## 4. Project Exploration Journey

A visitor browsing the portfolio without a specific project in mind should be able to discover interesting work quickly.

### Journey

```text
Projects
    ↓
Category
    ↓
Project Cards
    ↓
Filter by Tags
    ↓
Project
    ↓
Related Projects
```

Projects should be visually presented in a way that encourages exploration.

The category structure should provide the initial organisation, while tags should allow more specific filtering.

The system should avoid overwhelming visitors with a large undifferentiated list of projects.

---

## 5. Contact Journey

Contact should be deliberately low-friction.

A visitor should be able to reach a contact method from the homepage without navigating through multiple pages.

Possible contact routes include:

- Website contact form.

- LinkedIn.

- GitHub where appropriate.

- Email.

The preferred route is the website contact form, but visitors should not be forced to use it.

The general journey should be:

```text
Any Page
    ↓
Contact / Social Link
    ↓
Contact Method
```

The contact form should be simple and should not require visitor accounts.

---

## 6. Education Journey

A recruiter or admissions representative may want to verify Joe's academic background.

### Journey

```text
Education
    ↓
Academic Milestones
    ↓
Qualification / Achievement
    ↓
Relevant Details
```

The initial information should provide a quick overview of Joe's academic history.

Additional information should be available where it provides useful context, such as relevant coursework, projects or achievements.

---

## 7. Experience Journey

A visitor interested in professional development should be able to review relevant experience.

### Journey

```text
Experience
    ↓
Experience Type
    ↓
Role / Activity
    ↓
Responsibilities
    ↓
Skills / Lessons Learned
```

The experience section should not be limited to traditional employment.

Work experience, workshops, talks and other relevant activities should be represented where appropriate.

---

## 8. About Me Journey

The About Me section provides visitors with personal context.

It should be accessible from the primary navigation and should complement the evidence provided elsewhere.

### Journey

```text
About Me
    ↓
Background
    ↓
Interests
    ↓
Engineering Motivation
    ↓
Career Direction
```

The section should help visitors understand the person behind the projects rather than simply repeating the contents of a CV.

---

## 9. CV Journey

The CV should be accessible without requiring visitors to search through the website.

The preferred journey is:

```text
Homepage
    ↓
CV
    ↓
Download / View
```

The CV should also be accessible from other appropriate professional sections.

The website should complement the CV rather than attempt to replace it.

---

## 10. Discovery Journey

An important secondary goal is to turn a short initial visit into deeper exploration.

The top-level content should therefore be designed to create curiosity.

For example:

```text
Interesting headline
        ↓
"How did this work?"
        ↓
Project
        ↓
Evidence
        ↓
Technical explanation
        ↓
Other projects
```

The goal is for a visitor who initially intended to inspect only one project to become interested in the wider engineering work.

This supports the objective of making the website feel like a window into Joe's engineering mind rather than a static collection of achievements.

---

## 11. CMS Project Creation Journey

The project creation journey should be significantly simpler than manually developing a new page.

The expected workflow is:

```text
Finish Project
    ↓
Open Dashboard
    ↓
Create Project
    ↓
Upload Cover Image
    ↓
Set Status
    ↓
Enter Required Information
    ↓
Add GitHub Link
    ↓
Add Optional Sections
    ↓
Add Media
    ↓
Configure Metadata
    ↓
Preview
    ↓
Validation
    ↓
Publish
```

The user should be able to save the project as a draft at any point where appropriate.

---

## 12. CMS Editing Journey

Existing content should be editable through the dashboard.

The expected workflow is:

```text
Dashboard
    ↓
Select Content Type
    ↓
Select Content
    ↓
Edit
    ↓
Preview
    ↓
Save / Publish
```

The CMS should make it easy to find recently created and frequently edited content.

---

## 13. CMS Override Journey

Custom page implementations should follow a more deliberate workflow than normal content editing.

```text
Edit Project
    ↓
Enable Override
    ↓
Warning
    ↓
Explanation of Consequences
    ↓
Explicit Confirmation
    ↓
Select Hardcoded Page
    ↓
Save
    ↓
Preview
```

The system should make it difficult to accidentally bypass the standard validation and structure.

---

## 14. Returning Visitor Journey

The website should support visitors returning after an initial visit.

Temporary banners and recently updated project indicators can help communicate what has changed since their previous visit.

A returning visitor should be able to quickly discover:

- New projects.

- Updated projects.

- Current development work.

- New achievements.

- Current announcements.

This should help the website remain relevant as Joe's portfolio develops.

---

## 15. Accessibility of Important Destinations

The following destinations should remain easy to reach:

1. Contact.

2. LinkedIn.

3. GitHub.

4. CV.

5. Projects.

These should be accessible from the homepage and should not require visitors to navigate through multiple layers of the website.

---

## 16. User Journey Principles

The website should follow these principles:

### Immediate understanding

Visitors should understand who Joe is and what he does within seconds.

### Curiosity-driven exploration

Interesting content should encourage visitors to investigate further.

### Progressive disclosure

Technical depth should be available without overwhelming visitors who only need a high-level understanding.

### Evidence-driven presentation

Projects should use real evidence to support claims about technical ability.

### Low-friction contact

Visitors should be able to make contact with minimal navigation.

### Multiple paths

Recruiters, engineers and other visitors should be able to use the website differently without the site becoming confusing.

### Consistent navigation

Visitors should always have a predictable route to the major sections.

### Efficient CMS interaction

Adding and updating content should require significantly less effort than modifying the website directly.

---

## 17. Success Criteria

The user journeys should be considered successful when:

- A recruiter can understand who Joe is within seconds.

- A recruiter can reach contact information from the homepage quickly.

- A visitor can reach the featured project immediately.

- A technical visitor can reach detailed project information without unnecessary navigation.

- Visitors can move between projects easily.

- Project evidence is accessible without excessive scrolling or navigation.

- New projects can be created through the CMS without modifying frontend code.

- Projects can be previewed before publication.

- CMS overrides require explicit confirmation.

- Important professional links remain consistently accessible.
